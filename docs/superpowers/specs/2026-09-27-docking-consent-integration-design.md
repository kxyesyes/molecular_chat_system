## 3. Backend and entry choice

| Alternative | Trade-off | Decision |
|---|---|---|
| Existing LocalTaskBackend + DockingInputStager + DockingExecution; local Vina initially, existing OpenSandbox executor only under an independently fixed server policy | Reuses task authority, leases, cancellation and evidence; no Temporal rollout or external service required for first integration. Needs small prepare/claim/ownership seams and C-only output-root injection. | **Recommended and selected.** |
| Call MolecularDocking/DockingToolAdapter directly from a Web turn | Short call chain, but would have to duplicate durable consumption, artifact authority and task lifecycle, and would entangle C cancellation with A2 drain. | Reject. |
| Require Temporal or enable OpenSandbox as the first C prerequisite | Existing optional implementations are valuable, but adds deployment/readiness and cleanup dependencies and conflicts with the initial real-harness sandbox-off policy. | Not first integration. Preserve their current contracts; no activation here. |

Separate orchestration backend from scientific execution backend: C v1 always selects the existing **local task backend**, not the Temporal canary selector. `execution_backend` is one immutable server choice (`local` initially; `opensandbox` only after its separate release). No browser/model backend field, environment mutation, broker auto-start, tool discovery during design, hidden fallback or second invocation after timeout. Pin the selected executor and tool policy before issuing a consent preview. Unavailable selected dependencies return unavailable, not a different executor.

**One execution owner, no second scheduler.** In this document “C coordinator” means C-specific methods and state attached to the existing `TaskRuntime`/`TaskRuntimeBinding`, not another service/class that schedules jobs. Only LocalTaskBackend schedules and owns executable tasks. `docking_consents` stores authorization/receipts, not a runnable queue. The Web adapter only validates/projects/subscribes; it never runs tools, retries tasks, owns a competing cancel event or independently releases task resources. No new polling daemon, broker, executor pool or generic workflow/state-machine framework.

The minimal internal seams are: `prepare_docking_consent` (existing stager, no backend call), `approve_docking_consent` (CAS then existing local submit on the fixed manifest), `cancel_docking_consent` (same runtime cancel owner, including pre-submit latch), and `get_docking_consent_view` (owner-bound projection, no execution). These names describe proposed TaskRuntime methods, not existing APIs. The pre-raw-call guard belongs inside `DockingExecution`'s existing execution lease; output opening belongs behind CompletionStore/secure-I/O checks. The existing `submit_docking` contract and all non-C callers retain their behavior.

The consent card is an **inline control for an already admitted ordinary chat request**, not a standalone substitute docking form. HTTP carries bounded uploads and explicit approval; `/ws` receives the original chat and clarification messages and returns request-correlated C state. Read-only `docking_watch` is only an attachment/reconnect mechanism, not C's sole Web integration. No second receiver, socket service or `/api/chat`. Model proposal, textual “yes”, report buttons, CandidateSet ACK, `docking_top_n` and `docking_ready_for_preparation` never authorize execution.

### 3.1 Mandatory ordinary-entry unit and end-to-end identity

Two increments share this one design: **C-exec**, the safe execution sublayer, and **C-entry**, ordinary-chat routing/clarification/projection. C-exec can be tested first but cannot be released as completed C. C-entry is owned by new `src/web/docking_request.py` plus narrow hooks in the existing WebDecisionRuntime; `src/web/docking_consent.py` projects its state back into the originating message. Neither unit schedules work.

1. **Original request.** Accept the ordinary `{type:"chat", message, ...existing flags}` on the same `/ws` receiver. Preserve the whole query/history snapshot; derive owner from the session and assign the existing server turn/trace IDs. Before the existing docking-blocked exit, a server-enabled C admission branch may assess this unchanged request. With C disabled, current admission and B1 failures are identical. With tools disabled, no C preparation/execution is admitted. Non-C requests keep the existing B1/A2 path; mixed/uncertain obligations cannot be silently reduced to docking or its supported subset.
2. **Proposal, not permission.** Reuse the current model lease/provider transport and its native/JSON wire selection for a closed `docking_preparation_v1` proposal profile. It is not a ToolSpec/model action and exposes no execution callback. Proposed DTO has exactly `version`, `kind` (`not_c`, `docking_request`, `docking_refinement`, `docking_observation`, `mixed`, `uncertain`), `unresolved`, `source_spans`, and `fields`. `fields` may name only receptor/ligand references and the four explicit grid/options inputs; each proposed value must identify an exact span in the current query or an owner-verified attached source. No consent, task IDs, executable/path/URL, score, capability or budget fields. Server validation checks the entire request, source-span coverage and consistency, resolves actual owned references, and recomputes missing fields; a model's confident `unresolved=false` proves nothing. Model-invented grid/file references reject or ask for input; they never become defaults. Unsupported additional requested work stays explicit and blocks execution. Model/protocol failure does not fall back to a manual success path or another provider.
3. **One C root and task.** On validated C admission, reserve a `docking_consents` draft in `AWAITING_INPUT`, assigning the future task ID once. Seal server owner, `origin_turn_id`, root trace, original-query digest, admission/profile revision and source-reference identities. No scientific backend task is started yet. Keep the bounded original query/history in the existing request-owned private memory; the consent table stores digests/IDs rather than chat text. This draft identity is reused through clarification, READY consent, execution and the report. No second task is created by approval, attachment or report rendering.
4. **Clarification/preparation.** Server emits a request-bound `docking_event` carrying the exact missing fields and safe instructions, rendered beneath that original chat message. Text clarification uses a closed C refinement frame `{type:"docking_refine", request_id, revision, message}` on the same receiver; files/options use the inline card's bounded HTTP upload with the same request handle/revision. The browser handle is a locator, never owner authority. Check session, current generation, original obligations and revision before accepting a refinement. Fill only explicit missing inputs. Changing an already fixed input is a changed request: revoke the old unused preview and require an explicit new chat request/consent, not a changed payload under the old task. Once CLAIMED, refinements are rejected. Late/stale or cross-owner replies cannot attach to the next chat turn. A conflicting/mixed follow-up does not dispatch a valid subset.
5. **Consent and execution.** Once verified files/grid exist, the server calls the prepare-only seam and publishes the sealed preview/card for that same root/task. A human must click its explicit approval control; neither another model reply nor “yes/run it” in chat can consume the nonce. Approval goes through §4's CAS and the existing runtime. Card controls, cancel requests and status updates all correlate `origin_turn_id`, root trace, preparation revision and fixed task ID. The original user request authorizes preparation/clarification, not the scientific side effect.
6. **Response and report.** Progress and the single C terminal update the same original message/task card. On success, server-side deterministic formatting consumes the verified completion once, giving exact energy/unit, input/grid/tool provenance and owner-authorized pose link. Record the bounded outcome/task/completion-digest reference in that conversation's history only once, with waiting/failed/unknown never rewritten as successful science. A follow-up such as “这个对接结果是什么” may propose `docking_observation` with no new input fields; the server must resolve an actually eligible same-owner C history reference, otherwise ask for clarification/unavailable. It renders the same reverified observation, never re-runs Vina or lets the model manufacture/round/re-score numbers. Full unrelated report schemas are unchanged; the C report is the request-bound projection described in §6, not the legacy unauthenticated report URL.

The C proposal profile is a small extension of `src/agent/decision_transport.py` and `src/agent/openai_compatible_model.py`, with a separate closed contract in `src/agent/contracts/docking_preparation.py`; it does not broaden OrdinaryIntent or B1 decision actions. C admission/source closure lives in `src/web/docking_request.py`. App wiring/capability presentation must distinguish “can prepare a consent request” from “approved/ready/executed”. Required server validation includes extra obligations and source ownership even when the model omits them; a keyword hit alone cannot authorize C.

### 3.2 C0 closed DTO and factual journal

Wire profile is `docking_preparation_v1`; native function name is `docking_preparation`, with exactly one function call and no parallel calls. Native arguments and JSON-mode content both decode the entire same envelope `{proposal: {...}}`; no text-prefix/suffix extraction, code-fence repair, alternative envelope or native-to-JSON retry. Proposal has exactly the five fields named in §3.1; `version` is the literal string `"1"`, `kind` is the listed enum, and `unresolved` is a native boolean. Unknown/duplicate keys reject at every depth. Bound decoded input to 8 KiB UTF-8, depth 8 and 256 nodes before model validation; reject nonfinite numbers, lone surrogates and custom/native-type coercions.

- `source_spans` is an array of at most 16 closed records `{source_id, start, end, role}`. `source_id` is `query`, `refinement`, or a server-advertised opaque attachment ID (<=128 characters); it is not a file path. `start`/`end` are native non-bool integers defining a nonempty half-open range of Unicode code points in the **unchanged** server-captured text/attachment descriptor. `role` is `request`, `field`, or `extra_obligation`. Bounds, source existence and owner/generation must be checked server-side. Attachment descriptors contain safe identity/type labels, not binary contents or local paths. A span is evidence to validate, not a proof that omitted clauses are harmless.
- `fields` is a closed partial object over exactly `receptor_ref`, `ligand_ref`, `center`, `size`, `exhaustiveness`, `num_modes`. Each present field is exactly `{value, span_indices}` with 1..4 distinct valid native integer indices into `source_spans`. Reference values are <=128-character exact server-issued source IDs; numeric values obey §4.1 with no string/bool coercion. Missing values are absent, never null/defaulted. The server independently parses supplied numeric text/owned source descriptors and requires agreement with `value`; a proposed reference is not mounted by merely matching its name.
- `not_c`, `mixed`, `uncertain`, and `docking_observation` require empty `fields`; `mixed`/`uncertain` require `unresolved=true` and cannot create an executable draft. `docking_refinement` additionally requires the server's live waiting request/revision; `docking_observation` requires an eligible owned history reference. Server-derived missing fields/extra obligations override proposal completeness. Whole-request admission, not schema validity, decides whether a draft is created.

Add a C-specific `DockingPreparationJournal` in the existing `decision_transport.py`, reusing the bounded factual-record mechanics of `IntentJournal` without relabeling a C call as `ordinary_intent`. Its closed record contains server `proposal_id`, root `trace_id`, segment `turn_id`, `query_digest`, refinement revision, model/capability generations, `phase="docking_preparation"`, `protocol_name="docking_preparation"`, `protocol_version="1"`, actual transport `request_id` (initially null), stage/history, bounded HTTP status/parser outcome/completion, and the existing sanitized model-call metadata. Task linkage is a separate server receipt after admission, not an ID accepted from model output. No input text, response body, nonce, cookies, headers or raw errors in this journal.

Transitions are `created -> validated -> dispatch_started -> response_received -> parsed`, with `failed` available before dispatch and `failed/cancelled/timeout` thereafter; terminal stages cannot advance or be overwritten by late parse success. Bind the actual transport request ID once before dispatch; pre-dispatch validation failure has null request ID and zero dispatch count. Persist/reserve the root proposal slot before the transport call, count a dispatched-but-uncertain call as spent, and retain its factual journal on parse failure/cancel. Use existing carry/budget persistence; no separate journal store. Bound each record to 8 KiB/8 stage entries, at most four proposal records per C root (initial plus three refinements). Invalid/missing durable counters block continuation; no reconstructed zero, automatic retry or new root hidden in a refinement. Native and JSON tests must observe the actual counted lowest transport, separate proposed/dispatch/completed/uncertain counts, and prove ordinary IntentJournal/profile bytes and semantics remain unchanged.

Use at most one proposal request per accepted original/refinement segment, at most three clarification segments per C root, and no hidden retries. Charge these calls and owned cleanup to the existing request budget/journal, carrying spent credit across refinements instead of allocating a fresh root budget. Missing/untraceable provider usage remains unavailable/conservatively reserved. Waiting input expires after 15 minutes without sliding renewal; expiry/generation change requires a new explicit request, never background continuation. The separate 15-minute execution-consent TTL begins only when READY is issued. Purely structured card updates need no model call. Provider admission children and the model reader settle under existing A2 rules **before** releasing the waiting/consent card as actionable; no model lease is retained across human waiting or scientific execution.

The existing `request_accepted` turn identifies the admission segment. C-specific `docking_event` phases `awaiting_input`, `awaiting_consent`, `running` and `terminal` carry the root identity, plus `segment_complete` only after that segment's model work has drained. This releases the input composer without emitting a false scientific-success `agent_result`/`complete`. Final C task terminal remains a different event, emitted once for that task view. The frontend must handle these phases explicitly and not leave the original decisionTurn spinner active or mount an unrelated new conversation. Non-C `agent_result`/`complete`, candidate/report DTOs and A2 drain semantics do not change.

**Exact dependencies, not scope deferral.** Implementation waits for landed/re-pinned ordinary A2/B1 admission/continuation/identity code and reviewed C-entry contract, then C0/C8 and the real E08 route gate must pass on that integrated revision. Multi-step requests may consume only actually available owner-verified upstream structure artifacts; a B1 ranking/CandidateSet SMILES is not a receptor or pose file. Producing an absent ligand structure, fetching a missing receptor, or executing a B2-dependent generation step remains the corresponding approved upstream producer dependency, not implicit permission for C to invent it. The original multi-step obligation must remain visibly waiting/unavailable until that dependency is satisfied, rather than claiming success for docking alone. The approved ordinary-chat MAGL file-backed case has no such producer excuse and is mandatory here.

## 4. Frozen input, identity and consent contract

### 4.1 Preparation is not scientific execution

Proposed `POST /api/agent/docking/preparations`: same-origin session-authenticated multipart request containing exactly `request_id`, `revision`, `receptor_file`, `ligand_file`, and one `parameters` JSON part. The request handle/revision must resolve to the owner's existing C chat draft; the endpoint cannot create a free-standing scientific request. No file-path, URL, SMILES-only, batch, runtime_config, executable, job_id, owner, timeout, progress_callback, cancel_event, backend or raw token-control fields. Unknown/duplicate fields reject. File-backed C v1 is the approved structured-sample subset reached through ordinary chat; legacy typed/SMILES callers remain unchanged, not silently accepted then rejected on a sandbox switch.

`parameters` has exactly `center`, `size`, `exhaustiveness`, `num_modes`; all four are explicit. Center/size are length-three native finite int/float arrays (not bool/string); size is positive and <=100 per axis, exhaustiveness native int 1..64, num_modes native int 1..50, matching staging. Center is in angstroms, size is box length in angstroms. No default/inferred grid. Effective energy_range is the existing fixed 3.0 and is displayed in the preview. Each file is nonempty and bounded by the existing 25 MiB stager limit; the selected executor's smaller bound also applies (OpenSandbox ligand <=10 MiB). Bound multipart parsing/body accumulation too, not just the final bytes object. Portable filenames follow the stager's existing rules; extensions cannot authorize tool selection.

Server uses the preparation/request ID and fixed task ID reserved at C chat admission, CASes its current draft revision into PREPARING only when the entire input set is supplied, copies the files once with `DockingInputStager.stage`, and verifies the resulting manifest. Preparation may write these explicitly requested private staging files, but itself starts **zero** receptor/ligand preparation executables, Vina processes, model calls, broker jobs or backend tasks; earlier proposal calls are accounted separately. No executable readiness probe is necessary to display consent; policy identity must already exist, otherwise preparation is unavailable. A preparation I/O operation itself remains owned if its caller disconnects/cancels. Do not introduce versioned staging directories or change the stager's same-task identity checks: READY inputs are immutable; a changed scientific request requires a new explicit root/task after old ownership is safely resolved.

Initial admission is deliberately small: one unexpired preparation per owner, at most 16 pending preparations across the C runtime, and one admitted C execution globally. Count unresolved staging/submission/cleanup against its slot; do not evict it to admit another job. Capacity exhaustion returns 409 for an owner's existing preparation or 503 for shared capacity, without dispatch; this is rejection, not a new queue. Enforce these reservations transactionally in the same table. A consumed task's replacement requires a new explicit preparation/consent only after its prior cleanup settles. No growing collection of timed-out workers behind a responsive UI.

### 4.2 Sealed server record

Add one narrowly scoped `docking_consents` table in the **existing task-runtime SQLite database**, with migration under the existing initialization transaction; no second DB/service. It records:

- schema `DockingConsent@1`; preparation/request ID (PK), task ID (unique), owner session ID, server-generated root trace and origin turn IDs, original-query digest, refinement revision, admission/profile revision and owned source-reference identities; the browser cannot supply any authority identity;
- immutable manifest locator (private), normalized receptor/ligand filenames, sizes and SHA-256, `ligand_mode=file`, existing `config_hash`, existing execution `input_hash`, existing runtime `request_digest`;
- tool name `molecular_docking`, adapter contract version, server `tool_policy_digest`, fixed execution backend, policy generation, preparation/runtime generation, issued/expiry times and effective execution budgets;
- SHA-256 of a fresh 256-bit approval nonce, `binding_digest`, consent state, dispatch receipt state, cancellation/first-failure receipt, immutable UI terminal decision if any, cleanup status, artifact grant expiry if any;
- version integer used for CAS. No raw nonce, cookies, keys, input bytes, absolute locator, unredacted exception or model text in public events/logs.

Reuse the existing hash algorithms, do not confuse them: `staging._config_hash` hashes normalized configuration; `docking_execution._input_hash` hashes receptor/ligand sizes/hashes/mode; `TaskRuntime._docking_request_digest` separately includes config hash. Tests independently recompute all three. `binding_digest` is SHA-256 of `b"medchat-docking-consent-v1\0"` plus sorted-key, compact, ASCII-escaped UTF-8 JSON (`allow_nan=false`) of the fixed fields above: schema, preparation/task/owner/root-trace/origin-turn IDs, original-query digest, refinement/admission revisions and source-reference identities, both file records, ligand_mode, center/size/exhaustiveness/num_modes, fixed energy_range, all three existing digests, tool/adapter/policy/backend/generation identities, issued_at_ms, expires_at_ms, vina_limit_seconds and operation_limit_seconds. Never hash arbitrary request objects. Nonce digest and mutable receipt/state fields are excluded. AWAITING_INPUT drafts cannot issue a nonce or binding digest until all required fields are sealed in READY.

`tool_policy_digest` binds the trusted versioned executor/preparation contract, executable or sandbox image identities from the separately authorized release manifest, output-root policy and budgets. It is not merely the string “Vina”, a mutable path, an environment-variable name, or an LLM version claim. Review/install of that manifest and verifying real tool identities are later authorized activities; none were probed here. A policy change revokes an unused preview; it never changes a running task's executor. Actual tool versions in results must agree with the pinned release identity or remain unavailable.

### 4.3 Preview, one-use claim, expiry

Preview response 201 contains schema, opaque preparation/task/trace IDs, redacted display filenames, sizes/hashes, normalized grid/options, tool/execution policy label/digest, binding_digest, expires_at and the approval nonce. Return it only to the owner with no-store; the UI holds the nonce only in memory, never URL, local/session storage, chat history or analytics. Preparation ID or digest alone is insufficient to approve. Lost nonce means revoke/expire this preparation and explicitly prepare again; it is not recoverable from a status API.

Consent TTL is **15 minutes**, measured by server time, non-sliding; `now >= expires_at` rejects. In-process monotonic elapsed time also caps it; process/runtime generation changes invalidate unused previews rather than reconstructing a longer lifetime after restart/clock rollback. Tool policy and input hashes must match both at claim and immediately before raw dispatch. A claimed job that has not started its raw call before consent expiry does not execute; consume the receipt and report expiration. Expiry after raw dispatch stops granting new actions but does not forcibly re-label already running science; its fixed operation deadline/cancellation contract governs it.

Proposed `POST /api/agent/docking/preparations/{id}/approve` body is exactly `{approval_nonce, binding_digest, confirm:true}`. Authentication comes only from `request.scope['agent_session_id']`, not body/header task metadata. Require one valid same Origin for C mutations, including cancel/revoke, even where middleware would accept absent Origin. A foreign/unknown resource yields the same 404; bad schema 422; mismatched/stale/expired own consent 409/410; dependency/storage failure 503 with no dispatch.

Claim order: authenticate and validate closed DTO -> load private owned record -> reverify staged identities and fixed policy -> precompute bounded public receipt -> **SQLite CAS** requiring READY, same owner/digest/nonce hash/version/generation and unexpired -> durable CLAIMED -> one backend submission using the already fixed task ID/manifest. Reserve the cleanup/submission owner before starting any async/sync operation. Commit ambiguity consumes/blocks the consent; never “restore READY” in an exception handler. Two processes racing approve produce one winner. A repeat from the same owner with the same proof returns its existing receipt/status only; changed proof rejects. The second request must not re-enter staging or backend submit. Cross-owner equal input hashes never share authority or an idempotency key.

Immediately before the **first raw executor call**, while holding the existing verified execution lease, a second durable CAS changes the receipt to DISPATCH_RESERVED after rechecking cancellation, expiry, hashes and policy. It is deliberately committed before the call. A crash between reservation and invocation sacrifices availability: “may have executed/unknown”, no retry. Existing completion reuse may validate an already authoritative result without a raw call; it cannot bypass C's ownership/UI-publication gate. An exception after a backend accepted a job or after completion commit is reconciled from actual receipts, not treated as a proven pre-start failure. Preserve the first observed primary failure; cleanup/storage errors are additional fixed diagnostics, not a success or a replacement cancellation.

## 5. Lifecycle and the A2/C boundary

Three independent axes avoid a false physical-stop claim:

| Axis | States and authority |
|---|---|
| Consent/dispatch | AWAITING_INPUT -> PREPARING -> READY -> CLAIMED -> DISPATCH_RESERVED; pre-claim drafts/previews may become REVOKED/EXPIRED. Missing-field refinement advances only the draft revision; READY inputs are immutable. All claim/reservation ambiguity is non-replayable. A consumed receipt never returns to READY. |
| Scientific task | Existing TaskStatus/events and DockingCompletionStore authority. Backend cancellation/failure/timeout is not rewritten just to unblock a UI. Use existing `CANCELED` spelling in TaskStatus. |
| C view / cleanup | View ACTIVE -> exactly one of SUCCEEDED, FAILED, CANCELLED, TIMED_OUT, UNKNOWN. Cleanup independently pending/settled/unresolved. C `CANCELLED` means interaction canceled, not proven process exit. |

Initial budgets in the pinned C policy: Vina <=300 seconds, whole operation <=420 seconds from successful consent claim (including queue/staging recheck/publish, never reset per phase). Preparation request has a 30-second response deadline; timed-out preparation is not approvable and its I/O remains owned until settled. Cancellation/operation timeout chooses the non-success view locally without waiting for SQL, provider, process, artifact or executor cleanup. C has **one 5-second logical control-feedback budget**, covering lock queueing and the opportunity to observe a completed physical send. By expiry the feedback gate decides `delivered` or `undeliverable`; it does **not** guarantee physical send/close completion or peer receipt. Cancellation-resistant send/close remains owned after that decision (§5.3). This is an event-loop/protocol budget tested with controlled clocks, not an OS latency bound. Browser transport-loss display says unknown and cannot auto-resubmit.

The existing shared sender uses a 30-second wait followed by cancellation drain. Passing it a shorter timeout does not solve C. Add a C-only feedback operation using the same sender lock and existing Web runtime ownership, **without calling `await_with_deadline` or awaiting `_settle` in the feedback return path**. Leave A2 send/close behavior and `decision_chat.py` unchanged. Slow or cancellation-resistant storage likewise runs off-loop under retained ownership. If the view terminal cannot yet be durably written, choose conservative non-success with `persistence_pending=true`; no scientific success/download grant is possible. Persist/reconcile later under the same owner. On restart unresolved view/dispatch state is UNKNOWN, never silently ACTIVE with replenished budget.

Cancel before dispatch invalidates unused consent and invokes no raw executor. Cancel after dispatch sets the existing execution cancel signal immediately, asks the existing backend/broker cancel path once, suppresses subsequent success publication and retains cleanup ownership. Repeated cancel shares the same operation. Disconnect from the currently attached C view requests the same cancellation; reconnect may observe the receipt but cannot resume/reinvoke science. Explicit HTTP cancellation works without a socket. An approved job need not have a subscriber to start; subscription loss is canceling only after attachment, not a requirement to keep an HTTP request alive.

The C cancel latch is reserved before submission and also covers the CLAIMED-but-no-task-row window. It is checked at the raw-dispatch fence and propagated to the backend's execution event; a missing task row is not permission to forget cancellation. Request handlers must not wait for the database cancel call before signaling a live local owner.

Success publication requires: authoritative verified completion, matching consent/tool/input identities, finite parsed pose evidence, no earlier accepted cancel/timeout/primary failure, and settled known local/remote cleanup. A single coordinator arbitrates that decision and immutable terminal receipt; the corresponding SQL CAS must be confirmed before sending success or issuing artifact authorization. Cancel racing an already confirmed success returns the existing outcome, not a rewritten terminal. Cancel/timeout winning before confirmed publication suppresses late science; a committed-but-not-yet-acknowledged result may be retained as private reconciliation evidence, never upgraded from an already emitted non-success. Inject delayed successful commit followed by raise and cancel-during-commit to prove this distinction.

Precisely, a storage write carrying a proposed successful view is a **candidate publication receipt** until the live coordinator acknowledges its completion and wins its one-terminal latch. Its late commit alone cannot authorize any GET/download. All active-generation read paths consult that latch; timeout/cancel can seal a conservative view while the candidate write is unresolved, then append its suppression/reconciliation receipt without rewriting scientific completion. For this initial local scope, runtime-generation change disables all prior C artifact grants and automatic successful-view reconstruction, including candidate writes that appear committed. Expose UNKNOWN/reconciliation-required and retain the evidence; do not guess whether a success frame was delivered before a crash. This intentionally trades crash availability for safety rather than claiming atomicity between SQLite, external execution and WebSocket delivery. Durable cross-restart publication recovery is not added by C v1.

Retain the existing runtime's asynchronous wrapper around each C synchronous call and shield it from caller cancellation until the actual callable returns; cancellation is sent through its cooperative event, not by canceling that wrapper. Register the wrapper before submission and remove it only on confirmed callable settlement. Apply this same narrow seam to preparation/validation/publication I/O. Do not create a second executor pool or attach the shared default executor to a per-task helper that shuts it down. CommandAdapter/service/broker still owe their actual descendant/reader/join/late-cleanup receipts. All retained operations belong to the existing task owner; a failed join or uncertain command remains unresolved even after its top-level result returns.

A2 is unchanged: accepted A2 turns still settle real workers/joins and hold their model reader lease before their terminal; C cannot transfer an A2 worker away to evade that requirement. C-entry's proposal/refinement segments use that same lease/ownership rule and drain before an actionable waiting/consent card is released. The **post-consent deterministic execution sublayer**, not the whole C entry, uses no model and acquires no model reader lease. Its bounded UI terminal does not release a still-running admission child, runtime resource gate or output-root lease. Independent chat/model switching remains governed by actual readers, and C resources/policy replacement is blocked while their cleanup is unresolved. Human waiting never holds a model lease; stale model/admission generations require revalidation and a new preview, not a new consumed execution slot.

Shutdown stops admission, revokes unused previews, requests active cancellation, gives <=5 seconds graceful UI/control handling and a separate <=10 seconds owned-cleanup observation window. These limits bound waiting, not deletion success. Remaining owners are explicitly unresolved, retain private state and prevent reuse/close-success; normal broker/runtime recovery handles only known owned resources. A process crash cannot promise a surviving Python thread: persisted receipts instead prevent replay and identify reconciliation work. No automatic science restart, new generic recovery daemon or operator-authority fabrication.

### 5.2 P1: explicit CommandAdapter ownership/settlement receipt

This seam is mandatory in the future implementation allowlist, **not** a read-only lower-layer assumption. Add a small `CommandOwnershipScope`/per-command receipt in `src/docking/adapters/base.py`, passed through an optional server-only base-adapter constructor argument. The C-owned service instance installs the same scope on its Vina/ADFR/Meeko/OpenBabel adapter instances, including `_refresh_adapters`; inherited wrapper methods continue calling `self.run` without new model/input arguments. Runtime creates the scope before invoking its C tool/service factory, retains it until settlement and never stores it on a shared registry tool. Non-C callers retain default signatures/results/errors; C construction must fail closed if its scope is dropped. No scope/receipt object is serialized into ToolResult, browser fields or scientific evidence.

Minimal contract:

- `reserve_command` runs inside `CommandAdapter.run` **before any thread/process creation**. It registers a server command ID and private task/root ownership in the existing task's scope. Receipt states are `reserved`, `spawn_pending`, `running`, `cleanup_pending`, `settled`, `unresolved`; scientific outcome is a separate fixed first-error/result field. Registration failure means no spawn. Scope sealing after the outer tool call forbids new command reservations but permits already-reserved spawners to attach their late resources.
- Receipt holds actual spawner thread, process/Job or process-group handles, capture-reader threads and cleanup operations. Register the Windows Job before invoking possibly blocking Popen; attach each process immediately on return, before assign/resume/reader setup can fail. Every failure path must retain any created handles even if its immediate cleanup also raises. The existing `_create_windows_suspended` and `_create_windows_until_control` therefore receive/advance this receipt internally. A daemon flag and a strong reference alone are not settlement proof.
- `snapshot()` exposes only fixed state/count/error-code facts to its server consumer, not commands/paths/outputs. A condition/event wakes the existing runtime's owned settlement wait. `settle()` is called off the event loop and never from the spawner/reader being joined. It succeeds only after the command callable has ended, no spawn reservation is unresolved, every spawner has **actually joined**, the owned process tree is proven stopped, capture readers/cleanup helpers have joined, and owned handles have been closed exactly once. `cleanup_done` in a worker's finally is notification, not proof that thread exit/join occurred. A cleanup error leaves `unresolved`; merely joining its failing thread cannot convert it to settled.
- Timeout/cancel sets the same stop latch before a pending Windows spawn can be claimed/resumed. A late-created suspended process is cleaned under its receipt, never handed off for execution after that stop. Claim-versus-cancel races have one owner under the existing condition lock, not two competing killers. POSIX creation/group/readers have the same receipt requirement; if Popen itself is blocked, its owned caller stays pending, with cancellation honored as soon as the owned process is available. No promise that cancelling an await prevents physical creation already in progress.

Service consumption is equally mandatory. For C, all cancellation, ownership-uncertain, timeout, progress-error and generic-error paths (currently around service lines 1090–1120), **including `_failed_job_response` at line 834 and phase helpers returning false**, consult the scope before deleting/quarantining job files or changing history. If settled, perform the existing own-job cleanup. If pending/unresolved, return/report a fixed non-success plus an out-of-band deferred cleanup obligation to the same scope; do not call `_discard_partial_job`, rename/quarantine, remove history, or permit downstream phases while a command may still access those paths. Preserve the first primary failure and add cleanup uncertainty separately. No “timeout implies safe deletion” branch; checking only the two top-level exception handlers would leave a bypass.

`DockingExecution.run_verified` consumes that scope before leaving its existing `task_execution` lease/snapshot context, on success and every error path. A returned raw ToolResult does not end ownership: while a command receipt is pending/unresolved, the existing owned execution worker remains in settlement under that lease and the C output-root ownership. The Web feedback path can already have terminated logically. Once physical settlement is proven, the same worker performs the deferred own-job/history cleanup exactly once under the retained boundary, then allows input snapshot/lease release. If deletion fails, quarantine only after settlement and keep cleanup failure truthful. Permanently unresolved ownership keeps the context/private state retained and blocks reuse/shutdown-success; it is not repaired by dropping the worker or starting a second cleanup thread/scheduler. A prior timeout/cancel remains that outcome even after successful late cleanup.

Source-level late-spawn records cannot survive an OS process crash as live handles. Persisted dispatch/uncertainty facts prevent re-execution and authorize no deletion based solely on a missing Python owner. Recovery must re-establish existing platform ownership or leave the private job unresolved; do not use PID/name heuristics. This is the same conservative crash boundary as §5, not a new process manager.

### 5.3 P2: C logical feedback deadline, retained physical transport

Add a C-only send entry in the existing sender/Web runtime, not an alternative sender service. It uses the existing socket lock and the existing runtime's retained operation set. Before scheduling `lock acquisition -> websocket.send_text`, reserve a transport operation record, immutable task/turn/sequence identity and send-generation token. Scheduling failure rolls the reservation back and closes an unscheduled coroutine. Physical send and physical close are distinct registered operations; neither is detached or mistaken for a done timer.

The C feedback waiter observes the physical task against **one absolute deadline** using a non-draining wait. If it finishes before the deadline and the token still matches, record observed local send completion once. If timeout/caller cancellation wins, atomically mark C delivery `undeliverable`, revoke the token, set the socket non-writable for further application sends and request cancellation once, then return the logical outcome **without awaiting physical cancellation/settlement**. No `finally: await _settle(...)`, `wait_for` that waits for cancellation, or call to `_Sender.close_failed_delivery` is allowed on this C return path. A task that swallows cancellation stays owned. Repeated cancel/shutdown shares that same operation/settlement, not another send or close attempt.

An operation that times out while waiting for the lock must recheck its token/writable/deadline after acquiring it and perform no physical send. An already in-flight send may finish much later; its completion callback records only cleanup facts. It cannot call the old `on_sent`, mark `terminal_sent`/delivery successful, activate a download grant, update history to success, clear a stop latch, remove an unresolved owner or emit another frame. The ordinary scientific TaskStatus is not rewritten by a delivery failure, but no **late transport success** can upgrade the sealed C delivery/view decision.

Physical close is requested through the existing socket's close-once claim and queued only after the in-flight physical send has settled; it cannot run concurrently on the same transport. It remains a registered cleanup operation if it also swallows cancellation. **No fresh close timeout, additional close await, or second 5-second budget is appended to control feedback.** The separate shutdown observation window may report unresolved send/close, but never converts it into closed/released. Socket/resource owner removal occurs only after every registered physical operation actually settles (or remains explicitly unresolved on a close error). Receiver exit/connection-loss callbacks must retain these operations in the app's ownership registry even after subscription removal; no early runtime/socket resource replacement. Non-C A2 calls continue their current drain-before-return/close behavior unchanged.

Bytes already handed to an ASGI send cannot be retracted: do not claim that no stale bytes can ever appear on the wire. The C frontend therefore also seals its cancellation/timeout/disconnect outcome and rejects stale task/sequence/generation frames, including a late successful frame. Arm its control timeout at the user's cancel operation and its operation timeout from the server's accepted budget; failure to observe an on-time response is unknown/undeliverable, never automatic approval/retry. A server-observed send completion is not proof of browser receipt. Tests must demonstrate both server no-late-success/no-release and client sticky terminal behavior; cancellation-cooperative fake sends alone are inadequate.
