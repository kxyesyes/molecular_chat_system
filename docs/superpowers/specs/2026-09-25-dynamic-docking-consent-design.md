## 3. Architecture and private storage boundary

```text
existing session/origin middleware + A2 live socket ownership
  -> admitted docking obligation / C input-and-confirmation component
  -> existing Agent store: immutable request, confirmation, one consumed slot
  -> B closed binding proof + dynamic WorkflowRunSession
  -> C request-local dispatch/control and validation views
  -> DockingInputStager.task_execution -> DockingExecution
  -> explicitly injected SandboxDockingRunner -> existing UDS broker
  -> private validated completion -> Session evidence/receipt
  -> same-owner HTTP artifact read (never broker URL or host path)
```

Use the existing Agent store for C metadata and existing staging/completion facilities for bytes. Do not create a second Agent database, workflow engine or shared general file registry. New server-generated job IDs are allocated before dispatch and recorded under the slot. They never come from browser/model arguments.

App assembly supplies validated `c_staging_root` and `c_output_root` to the C boundary. These are server constructor/runtime objects, not public configuration fields. Both must be private, owned, absolute, non-link directories outside the legacy docking work directory, static/template roots and any legacy history/result traversal domain. Reject overlapping/ancestor roots and unsafe Windows reparse/hardlink aliases using existing secure-file primitives. No fallback to cwd, `temp_docking` or a temporary shared directory when a root is absent.

`SandboxDockingRunner(socket_path, c_output_root)` is explicitly injected into `DockingExecution(..., raw_executor=..., allowed_output_root=c_output_root)`. C must not use the default executor constructor branch that chooses local from environment. Existing operator-provided broker transport configuration is consumed by app assembly; C does not read/store user credentials or alter broker credentials. Missing approved backend/configuration means `docking_backend_unavailable` before execution where determinable.

C inputs, raw pose, completion and extra files never enter legacy `MolecularDockingService` history. C publishes only the one validated pose in its public receipt. No legacy report/pose conversion endpoint is used. C-specific HTTP tests must prove old result, history, report and pose routes cannot find C assets even when the caller knows a C job ID. Private roots, not unguessable IDs, supply this isolation.

Storage cleanup remains bounded and uses existing staging/completion ownership checks. Pending unconsumed uploads expire with their request; they may be removed on existing lifecycle/opportunistic cleanup after confirming no active lease. A proposed fixed 24-hour availability limit applies to committed public C artifacts; downloads check it even before physical cleanup runs. Consumed/unresolved evidence and files are protected from automatic deletion until execution/cleanup authority is settled. Durable consumed tombstones survive byte cleanup. This is not authorization for a new retention daemon or broad disk cleanup.

## 4. Proposed closed types and input/consent semantics

All names in this section are **new C design interfaces**, not existing APIs. Keep them in `src/agent/contracts/docking_consent.py`; no arbitrary dict/expression/JSONPath extension language. Public JSON views are strict, forbid extras/duplicate keys/nonfinite values and retain existing context/observation limits. A C request/receipt metadata record is bounded to 16 KiB, IDs to 128 characters, SHA-256 to 64 lowercase hex characters. Raw input bytes never enter Agent metadata or the model conversation.

Use explicit C schema identifiers `DockingRequest@1`, `DockingConsent@1`, `DockingSlot@1` and `OwnedDockingReceipt@1`; the closed model arguments stay inside the existing decision envelope. These are independent of legacy `DockingInput`/`DockingOutput` version 1. Fingerprints include the C schema/profile version, and unknown versions cannot be coerced into legacy inputs.

| Type | Purpose / trusted fields |
|---|---|
| `DockingInputRef` | Server-issued ID, role `receptor|ligand`, accepted format, byte count, content SHA-256 and request revision. No host path or remote URL. |
| `DockingRequestRecord` | Owner user/session, root trace, socket/runtime generation, stable slot `docking-1`, input refs/digests, exact box, fixed parameters, tool/adapter/binding/backend policy revisions, manifest-relative locator, created/expiry bounds and root budget identity. |
| `DockingConsentRecord` | Request ID/revision/digest, owner/trace/socket binding, purpose-specific confirmation nonce digest, explicit approval time and expiry; never a model-generated approval. |
| `DockingSlotRecord` | One monotonic state record per root; request digest, stable job/dispatch identity, consumed state and settlement/uncertainty metadata. |
| `DockingCallArguments` | Exactly `input_ref` naming the authorized `DockingRequestRecord`; no literal structures, box, backend, commands or consent booleans. |
| `OwnedDockingReceipt` | Owner-resolvable execution/completion/pose references and hashes, finite parsed energy/unit, pose count, source/config/version proof, fresh/reused disposition and verified cleanup state. It carries no absolute paths. |
| `DockingExecutionControl` | Internal only: cancellation signal, single root deadline, cleanup reserve, stable dispatch ID and owned worker/remote settlement handles. Never serialized as tool arguments or accepted from provider objects. |

### Input scope

The user supplies both files and all six box values. `center` is exactly three finite JSON numbers; `size` is exactly three finite numbers with `0 < value <= 80` Angstrom, the stricter existing broker bound. Booleans/numeric strings/null/omission are rejected. Zero coordinates are valid only when explicitly entered; zero is not a missing-value default.

Use fixed disclosed values `exhaustiveness=8`, `num_modes=10`, `energy_range=3.0`, and manual box semantics. These are server execution policy included in the confirmation digest, not hidden defaults for missing user box data or model-tunable fields. Preparation by the existing broker worker is disclosed: authorized receptor/ligand preparation plus Vina inside that sandbox; no additional model-visible preparation calls.

Initial C accepts one ligand record, not an SDF batch or multiple receptor MODEL records. A bounded non-executing format/count check must reject malformed, ambiguous or multiple-record inputs rather than silently select the first. The canonical worker/parser must validate accepted content during execution too; a filename alone is not format proof. If a single-pair contract cannot be deterministically established using existing parser capabilities, input stays unavailable, not guessed or converted through local helpers.

Reuse `_read_upload_limited` and `DockingInputStager.stage` with C's stricter combined limits: receptor at most 25 MiB, ligand at most 10 MiB, and no larger than the injected broker's configured ceilings. Bound the entire multipart body including overhead and all fields before unbounded parsing; use the existing broker multipart limit pattern where the Web reader alone is insufficient. Server-generated portable filenames preserve only the accepted suffix; original upload names are optional bounded display text, never path authority or log content.

Stage only a complete accepted pair/box packet. An incomplete ordinary request asks for clarification; an invalid HTTP preparation packet returns a fixed validation response. Neither starts a model/tool action, backend probe, structure fetch or Vina. Changing a staged/confirmed pair, box or policy requires a new explicitly admitted root request, not mutation of the sealed record. Ranker flags, target search rows, B evidence and candidate ACKs do not authorize conversion into C files.

### Approval lifetime and identity

Consent is valid for at most **15 minutes** after issuing the human confirmation challenge, additionally bounded by the original request/socket waiting expiry and original root deadline. Confirmation, polling, nonce retries and resume do not extend any bound. Because the existing loop normally has a 300-second root budget, that shorter bound may expire first; 15 minutes is an authorization ceiling, not a new runtime allowance.

Bind to the same anonymous user/session, root trace, live A2 socket record, request digest, tool/adapter versions, B binding/requirements revision, A2 model generation and the server-owned OpenSandbox execution-policy generation. The latter pins the expected backend/image/policy identity without secret fingerprints. Generation change before consume invalidates authorization; a matching model name or UDS path alone is insufficient. Confirmation proves an explicit user interaction within this bearer session, not a legally authenticated human identity.

Disconnect, abandon, new accepted root, shutdown or loss of the live waiting record invalidates unconsumed consent. No reconnect/restart execution restore is introduced. Same cookie plus old IDs cannot reconstruct the missing socket authority. Confirmed historical output may still be read through owner-authenticated, receipt-verified download until its retention limit; that is read-only access, not permission to execute again. Unsupported stored versions fail closed.

## 5. Minimal actual HTTP/WS protocol

These are proposed C additions under the existing protected prefix. They do not replace normal chat, A2 controls or the reference ACK endpoints. The C component uses existing same-origin cookie handling and A2 turn IDs; no token in URL, credential UI or browser-supplied identity/capability fields.

1. A normal `/ws` `chat` frame enters reviewed A1/B admission with docking as a whole-request obligation. Until a complete approved request exists, the decision loop may clarify but cannot call docking or finish the obligation. A C-only `docking_input_required` event, emitted from the server's obligation state, carries trace/turn, the existing waiting continuation ID, a server-issued purpose-bound `prepare_nonce`, accepted formats and required box fields. It does not originate from LLM prose. A2 ends that waiting delivery with its ordinary result/complete pair.
2. `POST /api/agent/workflows/{trace_id}/docking/prepare` accepts bounded multipart parts exactly: `continuation_id`, `prepare_nonce`, `receptor`, `ligand`, `box` (strict JSON `{center, size}`). It requires the matching live socket waiting record and owner before staging. Reuse the A2 nonce/CAS discipline, but assign preparation/confirmation distinct purposes so a candidate ACK or generic continuation ID cannot mean consent. One accepted preparation consumes its preparation permission; exact retry may return the same prepared response only after comparing the complete bounded request digest and live challenge, never restage or execute. Changed bytes/box on a reused nonce reject. It returns request/input refs, hashes, box, fixed policy, revision, expiry and a new server confirmation nonce. No execution/model call.
3. The C component renders those exact fields, an initially unchecked explicit acknowledgement, and a separate confirm button. `POST /api/agent/workflows/{trace_id}/docking/confirm` accepts exactly `{continuation_id, request_ref, revision, consent_nonce, approve:true}`. Validate session, same live waiting owner, complete unchanged record, all versions and expiry. Commit confirmation via the C store boundary. Return an acknowledgement only; this endpoint neither claims the continuation nor consumes the docking slot or calls Vina. Reject extra box/path/backend fields. A changed display requires preparation of a new root, not hidden confirmation of revised inputs.
4. After successful human confirmation, the same socket sends `type:'docking_resume'` with exactly `trace_id`, `continuation_id`, `request_ref`, `revision`. This explicit C control does not misuse A2's free-text resume or accept new scientific parameters. Runtime reconstructs the original immutable obligations from its live record plus confirmed C record, validates versions/proof, then uses the existing single-use continuation claim. The model still chooses tool/clarify/finish; C is not a static workflow secretly run by HTTP confirmation. Only the authorized `DockingCallArguments` appear in its catalog.
5. Existing A2 `cancel` targets the active turn; abandon/disconnect invalidate waiting confirmation as above. C extends A2 validation to preserve the one-receiver, one-active-turn and serialized-send invariants. Preparation/confirmation/resume race with cancel/new-root under that request ownership; a committed confirmation does not resurrect an invalidated socket.
6. A settled scientific result exposes a same-origin URL from the server route builder: `GET /api/agent/workflows/{trace_id}/docking/artifacts/{artifact_id}`. It carries no path/consent nonce/session token. A bounded owner-only `GET /api/agent/workflows/{trace_id}/docking` returns saved C request/slot/availability status, no raw inputs or live model state. Reads cannot submit, resume, re-run, refresh a backend or restore authority.

Reuse A2's live waiting registry/nonce generation and the existing session middleware. C needs a narrow owner-and-live-socket lookup for the two HTTP mutations; it must not create a parallel conversation store. Current A2 is design-only, so its landed implementation must be rechecked before defining the exact helper integration. New C nonce purposes/state are real additions, not claims that the current continuation schema already accepts consent.

Missing/foreign/stale handle returns a fixed non-disclosing 404; malformed input 422; expired/conflicting same-owner state 409; unavailable store/backend admission 503. Mutation routes enforce same-origin/transport policy and require the live server-issued nonce, including when the existing middleware accepts an HTTP request without an Origin header. Unknown/invalid cookies cannot adopt a record merely because middleware issued a fresh session. Do not log nonce/cookie, multipart content, structures or raw exceptions.

## 6. Atomic root slot and permanent non-replay

Reuse the Agent SQLite transaction/CAS pattern, not only in-memory locks. Proposed narrow methods in `src/agent/persistence/base.py` and `sqlite_store.py`, with closed validation in new `src/agent/persistence/docking_consent.py`:

- `prepare_docking_request(...)`: owner-bound expected-state creation of the single immutable prepared request.
- `confirm_docking_request(...)`: exact request revision/nonce/expiry/version comparison and explicit confirmation commit.
- `consume_docking_slot(...)`: compare confirmed state, owner, trace, live runtime generation, immutable digests, remaining budget and stable job/dispatch IDs; atomically set consumed state before any broker POST.
- `settle_docking_slot(...)` and `get_owned_docking_record(...)`: exact expected-revision settlement and owner-filtered bounded reads; settlement never grants execution authority.

Names are proposed, and arguments must be typed/closed; these are not arbitrary metadata update endpoints. Store in one versioned `docking_consent` section of existing `agent_runs.metadata_json`, with a root-stable slot ID, using `BEGIN IMMEDIATE` and strict expected-record comparison. No new database/schema is proposed for Agent storage. Ordinary `update_run_metadata` must reject writes to this reserved section, as it does for existing protected metadata. Existing status/checkpoint/continuation writers must preserve it exactly and reject corrupt/oversized state; they cannot drop a tombstone on redaction, recovery or same-trace replacement.

| Slot state | Permitted action | Execution authority |
|---|---|---|
| absent / awaiting input | Clarify, prepare one complete request | None |
| prepared | Show exact record, confirm or invalidate | None |
| authorized | Validate and atomically consume once before dispatch | Only a committed successful consume result permits one caller to dispatch |
| consumed / dispatched | Settle or inspect; broker receipt may still be unknown | No further invocation, even if no completion exists |
| settled success/failure/cancel/timeout | Verify/read existing evidence or report failure | Never re-run |
| uncertain | Fixed failure/attention state and protected resources | Never re-run; no automatic reset |
| invalidated / expired before consume | Show expiry or ask for a new root request | None |

The consumed transition is conservative: a crash immediately after commit but before POST loses that invocation rather than risks duplication. A commit exception is not retried as a consume operation. Even if the write did commit, that caller does not dispatch. Later inspection may identify consumed state but cannot authorize a substitute caller. Corrupt/missing required state on an already admitted root is blocked, not reconstructed as an empty slot. A new sampling/docking attempt requires a genuinely new explicit user request and new confirmation, not an automatic new trace generated by recovery.

Operation identity covers root slot, owner, request/input/config hashes, tool/adapter/effective policy and backend generation, plus B obligation/source proof. Changing a decision ID, input hash, continuation nonce or model turn cannot allocate slot two. Duplicate model actions validate the saved settled observation and source closure; absence/uncertainty returns a fixed failure, not an adapter call. `run_verified()` must never be used to query a consumed uncertain job because it can invoke its executor when no completion exists.

Keep `factory.py` shared flags intact. The C effective request adapter exposes its real non-idempotent `.spec`, one logical attempt, closed ref schema and policy version. Route through a C request-local `step_dispatch` seam (already supported by `WorkflowOrchestrator`) so neither generic timeout wrapper detaches the real worker. Other tools retain their existing behavior. Journal settlement/event retry may repeat metadata writes under stable IDs; it must not re-enter a consumed dispatcher.

## 7. Exact private validation -> typed gate -> public receipt boundary

Do not feed public relative paths or URLs to existing filesystem validators. Do not insert `validated=True`, `real_execution=True`, fake gVisor/image/cleanup flags, or a forged internal proof object to make a receipt pass.

1. **Resolve inputs internally.** Owner/consent/slot checks resolve only the exact C staging locator. Within `DockingInputStager.task_execution`, verify manifest and immutable snapshots. Construct the legacy `DockingInput` private view with server-resolved receptor/ligand paths and exact configuration. The model/Session input record remains refs/digests; paths exist only inside this execution boundary. Internal callbacks/control are keyword arguments, not extras taken from model payload.
2. **Execute one sandbox job.** `DockingExecution` invokes the fixed runner through its `raw_executor` seam. Runner downloads the broker's validated artifact into its private output job root and retains real backend proof. Reuse the typed docking raw/canonical output validation from `docking_contract.py` at this private boundary, plus `AgentResultValidator`/`DockingResultValidator`; a small callable gate can be factored from existing adapter validation without changing legacy schema semantics or introducing the adapter's detached timeout worker.
3. **Capture authoritative completion.** Keep `DockingExecution` input re-verification, `_VinaPoseStreamValidator` content checks, exact `docking_<job_id>` containment and `DockingCompletionStore` hash/copy/commit handling. Only a verified, unambiguous committed completion can support public success. C treats completion authority ambiguity as unavailable even if a lower-level compatibility result reports qualified success. The original backend/image/cleanup provenance must survive into the evidence used by later validation.
4. **Validate the receipt against private files.** New `src/agent/harness/docking_execution.py` provides a request-owned resolver/validator view to Session. It loads the exact committed completion through `load_verified`, checks consumed slot and input/config identity, resolves its relative pose under the private root using secure handles, and builds a detached private `ToolResult` view. Re-run the original typed/domain gates on that view with the actual private file paths; compare receipt energy/count/hash/version/cleanup fields exactly with the verified completion and parsed bytes. On reuse/download, the file proof is rechecked rather than trusted from a boolean. No live object accepted from an executor/provider becomes authority by class name alone.
5. **Seal the public representation.** Session's request-local validator uses the checked private view solely to validate the corresponding `OwnedDockingReceipt`; it never copies resolved paths into the public result. C uses a dedicated closed receipt output schema, not a mutated legacy `DockingOutput`. The ordinary validator remains unchanged for legacy callers; the C-specific validator composes its existing checks, including common status/error checks and docking failure scrub, through a narrow request-local resolver. Session validation, checkpoint reuse and continuation integrity must all use this same C view, never skip domain checks because a receipt has no `pose_file`.
6. **Persist and present refs only.** Public `ToolResult.data` contains receipt ID, execution ID, pose ref, pose SHA-256, count, finite `binding_energy`, unit `kcal/mol`, input/config/proof identifiers and fresh/reused disposition. The existing `WorkflowArtifact.path` field may hold a validated server-generated relative logical reference for C transport compatibility, with a separate server-built download URL at Web projection; it is not used as an OS path. Internal completion-relative locators remain in owner-protected server metadata. No public `runtime_config`, broker internal ID, absolute path, raw manifest, receptor/ligand bytes or untrusted formatted text.

The Session ledger's `provenance.output_digest` hashes the accepted public data representation; `pose_sha256` hashes raw pose bytes. They are different concepts and must not overwrite each other. Include C proof/receipt identity in B's binding proof, ledger input binding and full observation seal before publication. Check all of them on reuse and continuation. The original legacy docking schemas and static callers remain compatible; C is an explicit new binding/output profile, not a silent global schema change.

## 8. Single budget, remote cleanup and finite UI failure

### One root deadline

C inherits one server monotonic root deadline `D` from original normal-request admission. User waiting, upload, confirmation, continuation, model calls, staging, queueing, sandbox provisioning/preparation/Vina, download, validation, cleanup and terminal delivery spend that same budget. No fresh allowance on confirm/resume. Persist spent/reserved budget identity for auditing, but never reconstruct a monotonic deadline across a restart; execution resume is unsupported.

Reserve a fixed C cleanup/delivery portion of **10 seconds inside the remaining root budget**, not in addition to it. Define `science_cutoff = D - 10s` and `send_cutoff = D - 1s`: at most nine seconds for cleanup proof after stopping science, followed by at most one second for the entire terminal result/complete delivery. Do not dispatch if there is no positive science allowance before `science_cutoff`. Stop scheduling science and signal cancellation of unfinished science at that cutoff; bound cleanup calls/proof waits by `send_cutoff`, not by a fresh nine-second timer started late. Terminal lock acquisition and both outbound frames share one delivery deadline `min(D, terminal_claim_time + 1s, terminal_claim_time + existing_shorter_send_limit)`, never a new timeout per frame. Existing shorter phase/send limits still apply.

At `send_cutoff`, if no eligible clean terminal outcome has already claimed the terminal-delivery guard, immediately select and attempt the fixed uncertainty/failure delivery described below; do not wait until `D` to discover uncertainty and then start sending. Finish or abandon delivery no later than `D`. Clip every call/lease/poll/stream/parser operation to its corresponding remaining allowance. The runner's current 420-second maximum, broker stage defaults and two-second cancellation timeout are ceilings only: each effective wait is `min(existing ceiling, remaining phase allowance)`. The ten seconds are not extra grace. No new model, Vina, broker HTTP or WebSocket send call may start at or after `D`. A delayed cutoff callback running before `D` has only the remaining fraction of the delivery interval; if it runs at/after `D`, record delivery unavailable and do not start a late send. Existing held cleanup/transport operations are cancelled/drained under retained ownership, without follow-up network calls for this request after `D`.

This is a real C2 extension, not satisfied by wrapping the runner in `wait_for`. Add trusted internal deadline/control parameters at `DockingExecution` and `SandboxDockingRunner` seams; pass bounded budget control over the existing UDS request separately from `DockingParameters`. Proposed `X-MedChat-C-Control` is a bounded strict JSON header with exactly `version`, `clock_id`, `issued_ns`, `science_deadline_ns`, `root_deadline_ns` and `remaining_ms`. Numeric fields are strict nonnegative integers, version is `1`, deadlines are rounded downward, and science deadline is earlier than root deadline. This header is built only by the server-owned runner; Web callers/model payloads cannot supply or override it.

No probing scientific submission is permitted.

For the verified supported topology only, broker compares absolute monotonic deadlines, rejects future-issued/expired/inconsistent values and uses the stricter absolute deadline and sent remaining bound; transit/queue time is deducted, never reset. It derives `send_cutoff = root_deadline - 1s` so C cleanup/proof acquisition also ends before the reserved delivery interval. A reboot invalidates pending control. Pin the control protocol in consent; the revised broker validates it before enqueueing and acknowledges revision/deadline identity on the submission response. An older broker ignoring the header cannot qualify as compatible: app assembly must pin the reviewed compatible implementation before any C POST. No best-effort negotiation that first executes against an unknown broker.

Propagate the deadline through the broker's existing queue/create/upload/run/read/cleanup ownership paths, clipping timeouts and refusing new science after expiry. Add only a per-job C control entry in the existing service-owned lifecycle; no new scheduler or broker database/schema is proposed. Restart uses existing cleanup/failure recovery, not C re-execution. ### Cancel and settlement

User cancel, disconnect, deadline, model switch and shutdown stop scheduling and signal the same `DockingExecutionControl`. Track local bridge worker, runner HTTP operations, remote job identity and remote cleanup to settlement. A2 retains its single model lease while an actual model consumer/owned execution remains live. Repeated cancellation cannot cancel the cleanup owner or release capacity early.

For a known broker job: request cancellation and acquire terminal/cleanup proof within the remaining cleanup allowance ending at `send_cutoff`, then observe that exact job's terminal state **and** successful cleanup with no unresolved owned consumer. Do not spend the final delivery interval on a new cancel/poll call. Existing broker `wait_terminal`/status and cleanup logic are reusable; expose/consume only the narrow required status proof. A 202 response, cancelled await, closed client, terminal-looking UI or `cancel_requested=True` alone is insufficient. Preserve the existing broker's stricter failure/unknown-identity states.

For submit acceptance uncertainty before a broker job ID is known: the slot remains consumed. Do not POST again even with the same idempotency key, and do not claim no remote job exists. Broker store has `get_by_idempotency`, but no such public runner lookup is assumed. Initial C reports `dispatch_uncertain` and protects the associated resources; any later operator reconciliation uses the existing broker's authority, not a new model/tool recovery API. Adding a bounded internal read-only lookup would require a separately reviewed C2 amendment, never resubmission disguised as lookup.

### Finite user-visible termination, separately retained ownership

Terminal outcome selection and delivery have a defined order, serialized by the existing request-owner finalizer, not by whichever send finishes first:

1. A clean success is eligible only when raw pose/receipt/Session evidence validation, unambiguous completion and actual local/remote cleanup are all settled. If that complete proof is ready and claims `terminal_delivery_guard` while `now < send_cutoff`, freeze that success and attempt result/complete immediately under the single delivery deadline. A raw completion file, pending cleanup or a retroactively supplied earlier timestamp is not an eligible success. Ordinary user cancellation with proven cleanup may similarly claim `cancelled`; a cleanly settled failure/timeout retains its actual reason. Once an eligible clean outcome has claimed the guard, late cancel/cutoff cannot replace it.
2. At `send_cutoff`, if the guard is still unclaimed, the cutoff branch atomically claims it for fixed failure/uncertainty, snapshots only independently verified earlier evidence and starts terminal delivery without waiting for cleanup again. At the exact cutoff or later, a newly ready completion loses eligibility to this branch. Use `failed` (or aggregate `partial` for earlier valid B evidence) with a fixed reason such as `docking_cleanup_uncertain`, `docking_dispatch_uncertain` or `docking_deadline_exceeded`, `requires_user_action=true`, and no C energy/download.
3. The guard is latched **before the first send**, not after successful delivery. Separately record `delivery_state=delivered` only after both frames complete, or `delivery_state=unavailable` on timeout/disconnect. A failed or partial send never clears the guard and never authorizes a second outcome/delivery attempt. Lock acquisition and both frames share the one capped delivery deadline; no new call starts after it or after `D`.
4. Cleanup/completion arriving after the cutoff branch claims the guard cannot upgrade the frozen public outcome, even if it arrives before `D` or before the error frame reaches the browser. Late settlement may update technical audit metadata only; it cannot publish energy/download, emit another result/complete, reactivate consent or free the consumed slot for another invocation.

This requires a narrow C finalization branch in A2 runtime/bridge: presentation completion is distinct from execution settlement. The Session action remains durably consumed/uncertain when cleanup is unresolved, not falsely marked successfully stopped. The C component stops its spinner on the fixed error/complete or socket closure and explains that docking did not complete safely and must not be retried automatically. If delivery is unavailable, close/abort the transport under its retained local ownership rather than wait indefinitely or open a new network operation after `D`; actual frame receipt cannot be guaranteed on a broken connection. A client-side bounded waiting indicator may show connection/result unavailable, but never infer successful cancellation or execution authority.

At or after `D`, do not start any new model/Vina/network call for this request, including cancellation, polling, delivery or retry calls. Already-owned uncooperative operations may physically outlive cancellation; retain and drain their handles, record the overrun, and keep affected execution capacity/model replacement/shutdown closure blocked rather than detach them. An unresolved remote identity or cleanup failure keeps the C admission gate blocked across subsequent requests; durable unresolved slot records must be checked at startup before admitting C again. A process restart must not clear this block. Separately authorized existing operator recovery may settle cleanup, but is not an automatic post-deadline call from this request and cannot reset the consumed slot. This is a fail-closed resource condition with a finite UI error, not an infinite UI spinner or an assertion that hard deadlines can kill every external operation.

If the existing lifecycle cannot represent this finite-delivery/retained-owner split, C2/C3 release remains blocked for a parent-approved narrow lifecycle change. Do not solve it by weakening A2 drain guarantees or adding a separate orphan scheduler.

## 9. Scientific acceptance and owner-bound downloads

Scientific success requires all of: explicit current consent consumed once; matching original input/config hashes and versions; a fresh actual Vina execution receipt for this root; finite parsed energy and positive pose count from the new raw PDBQT; matching private pose hash; real non-demo/non-fallback backend provenance; verified sandbox policy/image and successful cleanup; unambiguous completion; Session/B proof and requirement closure. Use deterministic scientific formatting. Vina's docking score is not experimental affinity, binding free energy, pIC50 or efficacy.

`reused_completion=True` supports a clearly labeled historical/read-only result, not a fresh package-8 run. A new execution may produce identical bytes/hash to a prior run; freshness is execution/dispatch identity and receipt evidence, not an artificial requirement that every SHA differ. Do not mutate output to force uniqueness. Repeated real acceptance requires separately explicit requests/consents and remains parent-authorized future work.

The artifact GET authorizes **before opening any file or querying an external backend**: valid current anonymous session -> exact owned run/slot/receipt -> eligible, committed, unexpired artifact -> private containment/identity/size/hash verification. Unknown, foreign, revoked, ambiguous or unsupported-version references disclose no bytes; no arbitrary artifact lookup based only on a guessed ID. Download permission does not depend on a still-live socket once a committed receipt exists, but cannot restore execution.

Reuse `DockingCompletionStore.load_verified` and secure snapshot/stream helpers; the broker's `ArtifactRegistry.open_registered` supplies the established streaming integrity pattern, not a new browser authority. Open a pinned verified file/snapshot rather than validate a pathname then hand the pathname to a later `FileResponse` reopen. Bound file size to the strictest existing C typed/domain/completion gate (including the current 64-MiB domain proof limit); truncate nothing into apparent success. Verify the digest before response bytes are authorized and ensure the streamed identity remains the same. Replacement, symlink/hardlink/reparse, size drift and mid-read corruption fail closed. Client disconnect closes the read handle, not a scientific job restart.

Use fixed media type `chemical/x-pdbqt`, server-generated attachment filename, `nosniff` and private/no-store cache policy. Do not expose Range/cache behavior until its verified-read semantics are covered; initial C rejects unsupported range requests. The returned URL is an authenticated route locator, not a bearer share URL. No cookie, nonce, raw path or broker secret is embedded in it. Legacy URL bypass tests are mandatory even though new routes are protected.
