## 5. Controlled application and browser boundary

### 5.1 Proposed launcher assembly, not an existing API

The proposed launcher constructs the real `MolecularChatApp` in an explicitly selected, nonsecret acceptance server profile, using `normal_chat_mode='decision_a2'` and an explicit `decision_wire_mode` **only after those A2 options land**. Later merged B/C profiles supply their approved permissions; the browser cannot select a mode/provider/backend or increase privileges. Production constructors/defaults, deployment configs and the module-level default app remain unchanged.

The profile must resolve, before service/model construction: a fresh private round directory; separate temporary Agent/session/reference/config stores; approved read-only scientific asset locators; an explicit report outdir; independent main-provider and generator configuration; and approved C backend/topology. No automatic checkout `.env` load, persisted user LLM settings, user history DB, asset download, index rebuild or registry mutation. Main credentials enter memory only from runtime environment or a local key manager during a separately authorized real run. Never serialize them into config/temp files, CLI arguments, logs or reports. A nonsecret locator/boolean does not confer readiness.

The baseline constructor reads user settings and creates services early; A2's opt-in alone is not this isolation seam. Proposed implementation may add a narrow explicit assembly dependency/profile seam in the existing app/config factories, with legacy defaults unchanged, after review. No monkeypatch of admission, route, model responses or registry tools in real mode; if safe assembly cannot be achieved narrowly, stop with an exact dependency blocker. Do not import `src.web.app` as a preflight shortcut if its module initialization would already read user settings or create resources.

Launch only a child process owned by this run on loopback, one server at a time, no reload, no production port takeover, no remote attach option, and no service kill/restart. The launcher owns the port binding and verifies the child's startup/identity via its inherited private control channel, not `/health` from an arbitrary listener. Use no access logging or raw subprocess stderr persistence; fixed structured startup/error records only. Close the child and its owned local descendants through the reviewed lifecycle, never kill by image name or sweep machine processes.

### 5.2 Real normal path and server authority

The path under test is:

`browser GET / → real session cookie → actual /ws → A1 admission → A2 owner/lease → real provider decision → B/C-authorized tools → sealed result/report/candidates → actual DOM mount → protected HTTP ACK → follow-up`.

Use the real middleware cookie in HTTP/WS, held only in memory. Do not fill `scope.agent_session_id`, directly call handlers/services, construct `PreparedDecision`, or submit trusted tools/requirements/metrics/identity from the collector. Original case text is the normal message. Candidate/report IDs must originate in real observed outputs. Render and mount the strict real candidate/report frames; only then invoke the actual confirm route through the UI and observe its successful HTTP ACK. Restore uses the actual protected route for an owned historical source, not a claim of new generation or restored execution authority. Other-user, same-cookie-other-socket, refresh and stale selection behavior must match the landed contracts.

The normal browser connection owns its receive path and the A2 server keeps its one receiver. The passive collector observes server emission/metadata and external UI evidence; it does not attach a second receiver to that socket or open a substitute execution socket. Keep bounded collection and sequential case handoff. A2 accepted turns require `request_accepted` before model work and one `agent_result`/`complete` when writable, subject to the reviewed C terminal split. Preserve strict `scientific_report`/`molecule_candidates` payload schemas without adding a turn ID. `complete` is stream termination, not scientific success. New follow-ups and complete clarified `resume` requests are distinct; nonce/socket authority is never synthesized for admission rejection. Adapt CHAT-003 only as a separately named normal-route scenario using full supported clarification, not by claiming the old direct-bridge test already proves it.

### 5.3 External-browser handoff and independent review

No usable repository Playwright/Selenium/Puppeteer dependency or browser driver has been identified. This design does not claim a callable CLI browser-automation interface exists. Recommend a **proposed external-browser handoff**: the actual launcher plus passive collector are separate from the UI operator, which is a user in a real browser or Codex using its existing CUA capability when available. The CLI installs no browser framework and does not automatically type, click, inject frames or run DOM scripts. A new browser-automation dependency would require a separate gate, not an implicit implementation detail.

Proposed handoff uses the launcher's bounded local observation/control channel: publish only nonsecret run/case/outer-round identifiers, the tracked prompt reference, current handoff state and expected observation requirements. This is a new narrow collector interface, not an existing Web API. It arms one expected case at a time without granting tools, identity or request authority. The operator sends the exact original prompt from the normal composer; the server observer associates that actual accepted invocation with the owned browser connection/turn/trace using in-memory owner binding and observed request identity, not a browser-supplied case ID, prompt hash alone or timestamp proximity. Any ambiguous/unmatched invocation remains incomplete. Do not expose a public unauthenticated observation endpoint; channel access is controlled by launcher ownership, while its published identifiers are nonsecret and never bearer authority.

Use the actual normal page, no synthetic candidate seeding, hidden lab route or DOM-only replay as live evidence. External user/CUA operates original case submissions and supplies bounded UI observations; HTTP/WS and passive server records supplement, not replace, that path. Check visible text/status, loading removal, partial/error persistence, report/source rows, candidate mounts, selection, follow-up binding and protected download. **Screenshot, DOM/mount observation and server-observed HTTP ACK are separate evidence classes**: a screenshot does not establish mount/ACK, a successful ACK does not establish visible rendering, and none alone proves scientific execution. If an operator cannot supply a required DOM/mount observation with available tools, report the missing evidence rather than infer it from a screenshot.

Element visibility, event/terminal counts, displayed-versus-sealed numbers/units and source associations can be checked deterministically from the corresponding observations; this does not promise that the CLI can obtain browser observations on its own. Open-ended capability/follow-up semantics may be reviewed by a **user or Codex reviewer independent of the tested provider**, using a bounded checklist of actual server capabilities and prior-turn context, recording the reviewer role and evidence references. User manual grading of every case is not required. The tested provider must not grade itself; an independent LLM/Codex semantic review also cannot replace actual scientific tools, deterministic numeric/truth/provenance checks or artifact verification.

C retains its current separate requirement: a human sees the exact current files/box/effective policy and explicitly consents for **each** new execution. P8-B does not authorize Codex/CLI to auto-confirm, treat semantic review as consent, or replay consent across rounds. Missing per-case authorization is partial/`requires_user_action`, even when an external UI operator exists. Missing UI operator, required browser observation or independent semantic review is likewise partial/not done. Starting one CLI command alone cannot complete this browser acceptance.

## 6. Evidence: safe raw ledger, normalized view and independent live gate

### 6.1 Bounded records at observation time

Keep three small concerns separate: passive capture at existing production boundaries, a pure deterministic normalization adapter, and independent live-evidence validation. Reuse existing state-store/event/model metadata; add a narrow passive observation seam only for facts actually missing after inspection of the landed tree. No extra scientific execution to manufacture receipts and no new evidence service.

Proposed private `safe-ledger.jsonl` is **raw in event order/meaning, not raw provider bodies or secrets**. Each closed record has schema version, launcher run ID, pinned revision/profile/manifest revision, original case ID, outer round, optional internal iteration, monotonic sequence, observation stage, observed timestamp/time-domain, existing trace/turn/event/decision/request/execution/source identifiers when genuinely present, bounded safe payload, and redaction/omission indicators. Collector sequence/run IDs may be created by the collector and labeled as such; provider/tool/source IDs must be copied from actual production observations, never invented to fill missing fields. Redaction does not grant authority. Do not persist cookie values, nonces, authorization headers, provider URLs with secrets, raw model responses/private reasoning, user settings, arbitrary paths or full report/trace dumps.

Observation stages distinguish admission, provider validation, dispatch attempt, transport response/error/cancel, decision validation/repair, tool start/terminal/reuse, durable result seal, candidate/report projection/mount/ACK, artifact verification, UI terminal and actual settlement. Each stage has an explicit field allowlist; generic object serialization, arbitrary metadata/error repr and raw request/response logging are forbidden. Preserve failed and repaired attempts and reuse paths; never record only successful planning completions. Record source timestamps when available and collector observation timestamps separately; no fabricated execution timestamps or comparisons of unrelated monotonic clocks.

Reuse `request_decision.metadata.request_id` and `request_attempts`, and the loop's actual `model_calls` join on `decision_id`. Attempts 0 is a configured/validation-stage record, not network evidence. Attempts 1 records dispatch intent/attempt, not necessarily provider success; require actual transport observation/response for the claimed stage. Cancellation may occur before `state.model_calls.append`; without a passive observation of that exact attempt the report is incomplete, not repaired from counters or the next call. Model/provider/mode/config epoch must match the run's captured configuration. Never equate local `decision_id`, native function call ID and transport request ID.

For tools, retain real invocation IDs, trace, input/output digest, status, version, typed provenance, source receipt, candidate/source binding and any reused observation identity. A model-requested tool is not an executed tool. Reusing an earlier result is recorded as reuse, not a fresh terminal execution; a successful final result cannot erase failed attempts. Scientific validators/tools, not provider text, determine numeric truth and provenance validity.

### 6.2 Exact P8-A input shape

Use detached `EvaluationCase` copies with a separately versioned, reviewed policy overlay under `scientific_acceptance.strict_report`; original JSONL has no such strict policy and is not edited by this design. The overlay is closed: `decision_source: none|scripted|live_provider`, `entry_path: component|isolated|ordinary`, `outcome: positive|expected_rejection|preserved_partial`, `require_new_pose: bool`. Live positives use `live_provider/ordinary`; rejection policies are frozen per original negative case at the intended validation boundary, not selected after seeing whether a provider ran. Missing/changed policy is a gate failure. A preserved-partial policy never turns positive scientific incompleteness into full success.

Normalized iterations retain the existing structure:

```text
iterations[] = {iteration: 1|2|3, case_count, status, results: [case rows]}
case row = {case_id, status, actual_skill, actual_tools,
            events: structured events, tool_provenance,
            truth_checks: named status/detail records, anti_hallucination, ...}
evidence = {run_id, revision, sources, artifacts, cleanup}
sources[] = {case_id, round, run_id, revision, trace_id, proof_class,
             decision_source, entry_path, provider_request_ids,
             tool_execution_ids, demo_mode, fallback_used}
artifacts[] = {case_id, round, run_id, revision, trace_id, step_id,
               artifact_id, binding_energy, unit, byte_size,
               producer_sha256, observed_sha256, tool_execution_id, created_run_id}
cleanup[] = {round, run_id, revision, ownership_released,
             process_cleanup_complete, state_cleanup_complete}
```
