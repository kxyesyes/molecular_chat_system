# 分子对接结果明细展示设计

## 目标

让普通单次对接、持久化对接和历史恢复三条前端链路都展示同一份逐 Pose 的真实 Vina 结果表，视觉上接近参考截图，但不把缺失数据补成伪造数值，也不把不匹配的历史受体与配体拼接成复合物。

## 已确认范围

- 覆盖普通单次对接结果。
- 覆盖新的持久化任务结果。
- 覆盖历史任务恢复结果。
- 批量对接保留现有批量汇总表，不在本次改动中强行改成单次结果表。
- 增加一个一键示例入口，载入本地登记的 PDE4A apo 结构 `6FG5` 和罗氟司特 SMILES；示例不会自动提交对接任务。
- 不改变 Vina、ADFRsuite、Meeko 或任务运行时的科学计算逻辑。
- 不引入 React、Vue、前端构建链或新的第三方依赖。

## 现状与问题

旧版单次对接路径已经在 `showRealResults()` 中渲染逐 Pose 表格；历史恢复路径能够从 PDBQT 解析 Pose，但样式和入口与新链路分离。持久化任务路径的 `renderDurableTaskSuccess()` 只展示最佳结合能和构象总数，因此新链路无法看到截图中的逐行结果，也无法从结果表直接查看指定 Pose。

持久化任务的科学结果已经以受完整性校验的 `result.pdbqt` artifact 保存。结果明细应从该已验证 artifact 重新生成，而不是信任浏览器提交的数值，也不应把任务摘要中的构象数量复制成多行。

## 方案与取舍

### 方案 A：浏览器直接解析 PDBQT

前端请求现有结果文件并解析 `REMARK VINA RESULT`。

- 优点：改动小，复用现有下载接口。
- 缺点：科学结果解析逻辑继续在前后端重复；配体效率等后端计算字段无法可靠复用。

### 方案 B：把所有 Pose 行永久写入任务摘要

扩展持久化 completion manifest，把每个 Pose 的行数据作为结构化结果保存。

- 优点：读取速度快，前端不需要解析文件。
- 缺点：需要扩展完成清单 schema 和兼容旧 manifest；重复保存可从 artifact 重新导出的数据。

### 方案 C：增加有归属校验的服务端结果明细投影（采用）

新增只读结果明细接口。接口先复用现有任务归属与 artifact 完整性校验，再在服务端调用已有 Vina 解析器生成逐 Pose 行；前端只负责统一渲染和触发已有 3D 查看器。

该方案保持科学解析单一来源、兼容旧任务、避免扩大持久化 schema，并满足普通任务与持久化任务使用相同展示契约。

## 后端设计

### 明细接口

在现有 docking route 中增加一个只读 JSON 投影，例如：

`GET /api/docking/result/{job_id}/summary`

接口复用 `read_owned_docking_pose()` 的 session、旧版记录/持久化任务归属和 artifact 读取检查。读取成功后使用 `MolecularDockingService.parse_vina_results()` 生成：

```json
{
  "success": true,
  "job_id": "...",
  "total_poses": 3,
  "results": [
    {
      "pose": 1,
      "binding_energy": -8.4,
      "rmsd_lb": 0.0,
      "rmsd_ub": 0.0,
      "ligand_efficiency": null
    }
  ]
}
```

`ligand_efficiency` 只有在后端有经过验证的重原子数时才返回有限数值，否则返回 `null`；前端显示“未计算”。解析失败返回明确的非成功响应，不返回空行或默认分数。

### 3D 查看边界

结果表的“查看”动作继续调用现有 `viewPose()` / `loadComplexStructure()` 链路，并使用服务端返回的 Pose 编号。持久化任务的最佳 Pose 使用后端明确提供的 `best_pose.pose`，不默认映射为 Pose 1。历史恢复在当前受体未恢复或不匹配时仍只展示数据，禁用复合物查看按钮。

## 前端设计

### 一键示例

在蛋白质输入区域放置一个小型“载入示例”按钮，按钮文案明确标注 `PDE4A apo（6FG5）+ 罗氟司特`。点击后从本地服务端读取已登记的 `data/samples/PDE4A_apo_6FG5.pdb`，通过浏览器现有文件输入契约载入蛋白，并把 PubChem 结构标识对应的罗氟司特 SMILES 填入单分子输入框。按钮只准备输入、更新预览和对接盒状态，不自动提交 Vina 任务；文件缺失时显示可操作的错误，不回退到其他结构。

示例结构身份、来源、下载日期和 SHA256 保存在 `data/REGISTRY.md`。这份示例使用真正的 apo PDE4A 结构 `6FG5`，不把 `1XOQ` 复合物结构标称为 apo。

### 统一渲染契约

在 `src/web/static/js/docking/ui_manager.js` 中抽出统一表格渲染函数，输入为经过接口或旧版结果解析得到的：

```js
{
  job_id,
  total_poses,
  results: [{pose, binding_energy, ligand_efficiency, rmsd_lb, rmsd_ub}],
  best_pose
}
```

普通单次结果、持久化完成回调和历史恢复都调用此函数。每个字段均经过有限数值检查；不可用值统一显示“未计算”，绝不以 `0`、Pose 1 或其他默认值填充。

### 视觉与交互

- 结果卡片保留现有页面风格，使用浅蓝完成状态条、紧凑表头和圆角能量标签，接近参考截图但不复制其内部任务 ID 展示。
- 表格列为“结构编号、结合能 (kcal/mol)、配体效率、RMSD下限 (Å)、RMSD上限 (Å)、操作”。
- 结合能标签只做视觉强调，不文案化为实验结论。
- “查看”按钮切换对应 Pose 到 3D 查看器；查看失败显示明确错误，不清空已有合法结果。
- 桌面端使用表格；窄屏使用横向滚动，保证数值列不被压缩成不可读状态。
- 主结果区域显示完成状态和构象数量；内部任务标识放入可展开的详情或保留在下载/历史动作中。

### 错误与兼容

- 明细接口失败时保留已验证的汇总信息，并显示“结果明细暂不可用”和重试入口。
- 历史任务明细失败不显示空结果表，避免把“无法读取”误认为“无 Pose”。
- 旧版结果与持久化结果继续支持下载；不改变已有结果文件路径契约。

## 测试与真实验收

先写失败测试，再实现：

1. Python route 测试：普通记录和持久化任务返回逐 Pose JSON；未归属、缺失 artifact、非法 PDBQT 均拒绝或返回明确错误。
2. JavaScript DOM 测试：三条链路都渲染相同列；数值缺失显示“未计算”；行按钮传递真实 Pose 编号；历史受体未恢复时不生成查看调用。
3. 现有 docking 结果、历史、任务所有权和安全渲染回归测试。
4. `compileall`、相关 `node --check` 和前端契约测试。
5. 启动真实项目后，从前端完成实际对接，确认表格行数、能量、RMSD 与真实 Vina 输出一致，并点击至少一个 Pose 验证 3D 查看器切换；再从历史面板恢复同一任务验证展示与受体绑定边界。

## 不在本次范围

- 不改变 Vina 搜索参数、评分方法或对接算法。
- 不新增实验活性、结合常数或其他未经工具输出支持的科学指标。
- 不重写批量对接结果模型。
- 不自动删除或迁移已有历史文件。
