# 沙盒清理截止时间测试分层

## 已批准的范围

用户明确批准将逻辑截止时间与真实存储集成验证分离：0.5 秒改为逻辑时间预算，不再声称是机器墙钟性能保证。保留 run grace=0.02、destroy hard timeout=0.03、stop timeout=0.05，不改生产代码、CI 超时或科学校验，不跳过用例。

起点为 main 的 `e2cb6f7`，使用独立分支 `codex/sandbox-cleanup-deadline`；不混入 P03/P04/P05。PR #34 的原始 CI 失败必须保留：0.51840058 秒未满足墙钟 `<0.5`。受控存储延迟能复现相同断言，但不能据此断言 Linux CI 的具体慢点。

## 设计

1. 测试专用可控时钟仅作用于当前事件循环，显式推进逻辑时间，真正驱动 asyncio 已注册的超时回调。不 mock wait/wait_for、不伪造 TimeoutError、不自动推进越过 runnable tasks、不改变全局 monotonic 或事件循环策略。退出时恢复原时钟与分辨率。
2. 原场景继续执行真实 SandboxBrokerService 与临时 SQLite、取消抵抗 fake SDK。在取消前开始计时，首次 stop 返回 StopIncomplete 后结束，保持 `<0.5` 逻辑预算。分别验证期限前仍等待、期限后转入下一阶段，防止保留总预算却丢失单步超时覆盖。
3. 非逻辑时钟的真实 SQLite 集成场景保留失败状态/错误码、超时后任务继续被持有、释放 SDK 后最终清空及无泄漏。覆盖正常和注入存储延迟，不将该场景结果称作真实 Vina 验收或端到端性能通过。
4. 所有场景在 finally 释放取消抵抗 SDK、收尾服务和测试任务。中间断言失败也不能令 asyncio.run 退出时永久等待。
5. 用变异探针证明测试能拒绝 run/destroy/stop deadline 延长、提前超时及丢失任务跟踪；辅助时钟自身验证回调顺序、取消回调、ready 队列与作用域恢复。

## 边界与风险

- 测试时钟如需访问 CPython loop 的 ready/timer 队列，必须局限在测试 helper、明确不支持任意网络/线程 I/O 的虚拟推进，并给循环推进设置有界失效保护；不引入生产抽象或第三方依赖。
- SQLite 操作仍是真实执行；逻辑时钟不计入操作墙钟耗时。真实存储性能是否满足 0.5 秒尚未证明，不在本次修复结论中。
- 未执行真实模型、生产沙盒或数据库迁移。不得把本地通过视为 #34 的 CI 已通过。
- 本轮先本地修复与独立审查，后续发布/合并遵守仓库授权门禁。

## 验收

辅助时钟与新增场景聚焦回归、原失败用例重复运行、sandbox-core 全回归、源码编译、diff 检查；原生产文件和 CI 文件必须零差异。独立规格与质量审查通过后报告准确红绿记录、跳过项与剩余事项。
