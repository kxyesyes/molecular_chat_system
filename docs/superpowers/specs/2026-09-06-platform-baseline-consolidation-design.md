# MedChat 平台基线收敛设计

## 目标

把当前相对共同基线累计 537 个提交的长期开发链，收敛为一个可审查、可验证、可通过 Pull Request 进入 `main` 的平台 V1 基线，同时完整保留原始提交历史和所有未提交用户改动。

## 当前事实

- `origin/main` 位于 `ed8c150`。
- 本地 `main` 位于 `3b87853`，比 `origin/main` 多 2 个文档提交。
- 当前功能分支 `codex/target-search-authoritative-fallback` 位于 `d3d4fbb`，相对与 `main` 的共同祖先多 537 个提交，同时缺少本地 `main` 的 2 个提交。
- Agent 科学可信基础、LangGraph、Temporal、OpenSandbox、Web 修复和权威靶点检索等里程碑均是当前分支的祖先，说明这些提交构成一条长期开发链，而不是多个随机合并分支。
- 原始工作树 `D:/MedChat/molecular_chat_system` 有已修改和未跟踪文件，不能执行 reset、clean、checkout 覆盖或历史改写。
- 当前工作树中的 `data/molecular_faiss_index.index.manifest.json` 是既有未跟踪文件，必须保持未跟踪且不得进入基线。
- 当前 CI 凭据扫描会命中 3 个包含假 `sk-...` 测试夹具的文件；在创建平台基线 PR 前必须消除误报并确认没有真实凭据。

## 方案选择

采用“一次性平台快照基线 + 永久历史归档”，不在原分支上 rebase 537 个提交，也不直接把当前分支合并进 `main`。

选择该方案的原因：

1. 原始线性历史仍由归档分支和标签完整保存，可随时追溯。
2. 新基线只表达最终可运行状态，避免把数百个中间修复提交带入主线审查界面。
3. 不改变任何现有分支提交，不需要 force push。
4. 合并后所有新任务都可从新的 `main` 建立短生命周期分支。

不采用以下方案：

- 不直接 merge 当前分支到 `main`，因为 537 个提交无法进行有效审查。
- 不对当前分支执行交互式 rebase，因为冲突面过大且会改写审计历史。
- 不在原始脏工作树中执行迁移。
- 不删除旧 worktree、分支或未跟踪文件。

## 分支与备份结构

建立以下永久或阶段性引用：

```text
codex/archive/platform-stack-2026-09-06
    -> 当前完整开发链 d3d4fbb 及其后续基线准备提交

codex/archive/local-main-docs-2026-09-06
    -> 本地 main 的两个未推送文档提交 3b87853

codex/platform-v1-baseline
    -> 从本地 main 创建，应用长期开发链的最终文件差异
```

同时创建带注释的本地归档标签，记录原始 SHA、测试状态和生成日期。归档引用在平台基线合并并稳定运行前不得删除。

## 数据保全边界

原始工作树的未提交修改不纳入平台基线，也不自动提交。迁移过程只读取其状态并生成文件名清单，不读取或复制敏感内容。所有历史整理均在新的独立 worktree 中完成。

以下内容明确排除：

- `data/molecular_faiss_index.index.manifest.json`
- `.env`、真实 API Key、token、密码和本机密钥文件
- `outputs/`、`scratch/`、运行日志、SQLite 运行库和模型权重
- 原始工作树中的未提交修改和未跟踪业务文件

## 基线构建流程

1. 创建并验证归档分支与标签。
2. 为本地 `main` 的两个文档提交建立独立备份分支。
3. 从本地 `main` 创建 `codex/platform-v1-baseline` 和新的独立 worktree。
4. 以 `git diff --binary main..codex/target-search-authoritative-fallback` 表达最终树差异，并只在新 worktree 应用。
5. 检查差异是否意外删除本地 `main` 文档或引入运行产物。
6. 将基线按责任拆成少量可理解的提交；若文件交叉依赖导致中间提交不可运行，则保留一个明确的 `chore: establish MedChat platform v1 baseline` 快照提交。
7. 修正假凭据测试夹具，使 CI 扫描在不降低检测规则的前提下通过。
8. 执行完整测试、真实验收、编译检查、前端静态测试、密钥扫描和大文件检查。
9. 推送基线分支并创建 draft PR；不得自动合并。

## 验证门禁

平台基线只有同时满足以下条件才允许创建 PR：

- `git diff --check` 通过。
- Python 全量测试通过；环境依赖导致的 skip 必须列明。
- Agent contract 验收通过。
- Golden real 验收中的 partial/failed 原因必须真实记录，禁止改写为 passed。
- JavaScript 语法和现有 Node 回归测试通过。
- CI 使用的凭据扫描命令返回无命中。
- 新基线不跟踪 `.env`、数据库、模型权重、输出目录或 manifest。
- 不存在超过仓库既定限制的新增大文件。
- 原始工作树状态在迁移前后完全一致。

## PR 策略

本地 `main` 的两个文档提交通过单独分支保留。平台基线 PR 默认以远端 `main` 为目标；如果文档 PR 尚未合并，则平台基线先以文档分支为基底，待文档 PR 合并后再将目标调整为 `main`。

平台基线 PR 必须包含：

- 原始开发链归档引用；
- 基线来源 SHA 和目标 SHA；
- 文件范围与主要子系统；
- 全量测试和真实验收结果；
- 已知 partial/skip 原因；
- 凭据扫描和大文件扫描结果；
- 审查重点与回滚方式。

只允许维护者手动合并。合并后保留归档分支至少一个稳定发布周期。

## 回滚策略

迁移过程不改写任何已有提交，因此任一步失败时只需删除新建的基线 worktree 和未合并分支。原始开发链、原始工作树和本地 `main` 均保持可用。若基线 PR 合并后出现问题，使用普通 revert PR 回退基线提交，不对 `main` 执行强制重置。

## 完成标准

- 有可验证的永久归档引用。
- 有一个从稳定主线构建、无运行产物和无真实凭据的平台基线分支。
- 基线通过约定测试门禁并创建 draft PR。
- 原始脏工作树未被改变。
- 基线 PR 未被自动合并。
- 后续任务可以从更新后的 `main` 使用“一任务一分支一 PR”的正常流程。
