# 首页多配体对接实施计划

目标是在现有首页完成受体核验、一张批量确认单、一次执行和逐配体结果交付。实现沿用 FastAPI、原生 JavaScript、SQLite 任务库和本地 Vina。

- [x] 在 `src/web/docking_batch_request.py` 实现显式清单与会话候选解析，先用定向测试覆盖用户给出的两类请求、乱序候选、无效输入和会话隔离。
- [x] 将批量输入绑定至 `docking_chat_controller.py` 与 `docking_coordinator.py` 的受体准备流程。核对受体和配体内容摘要，以已确认参数生成只属于本批次的确认凭据，阻止通过单配体端点执行批次。
- [x] 使用 `docking_batch_execution.py` 和对接路由实现一次执行、逐项状态及按所属会话读取的构象。验证取消、重复确认、部分失败和资源释放。
- [x] 在首页对接卡片展示清单、确认和批次结果。用 Node 测试核对输入顺序、失败行、刷新和下载，在原有单配体回归中验证兼容性。
- [x] 运行真实浏览器与 Vina，检查批准前后执行记录、输入身份、构象数和文件摘要。按实际结果记录通过项和限制。

真实首页验收使用 Chrome、首页配置的云端聊天模型和本地 Vina。同一已核验的 6SAM 受体分别接受显式清单和按 3、1 点名的同会话候选。两批均在双击确认后创建一个父任务，每行各执行一次，刷新只读取状态。四份下载均与各自完成记录的 SHA-256、最佳评分和构象数一致，另一浏览器会话读取状态和构象均返回 404。候选越界和第二个 SMILES 无效时页面显示对应项，确认前取消后执行任务数为零。部分失败由受控执行器单独覆盖。

验收还发现已提交批次的确认草稿阻塞下一次对接。修复后，同一连接可以在第一批获批后立即发起配体顺序相反的第二批。确认前取消第二批后，第一批的构象仍可下载，应用正常关停。原单配体入口也通过真实确认、下载和跨会话拒绝读取验证。
